## C1. One clock with CPU-owned positions

**Revise B5: retain the plugin clock as owner for CPU providers. Publish one coherent position snapshot to native geometry, rather than making a Desmos ticker feed an unnecessary round trip through JS.** Use a ticker only for a native-math mode that actually computes its geometry in Desmos. Neither clock should independently advance the other.

Recommended option (c), for the current provider and randomized replay:

1. Warm/build the provider before starting playback. Each presentation tick computes `at(t)` once. Keep the returned double-precision values as the sole authoritative frame snapshot.
2. Publish a single owned numeric list containing positions and a frame ID. Native scalar definitions such as `a_{N1}=L_{N}[1]` refer to it. Update only that list's LaTeX, using an existing expression ID; don't rebuild folders or the entire graph. Keep velocities/flash state in that same snapshot if native geometry needs them. Do not let the compiler expand replay lists into every GPU field evaluation: continue supplying the resulting numeric scalars as uniforms.
3. Start at **30 geometry updates/second**. Feed the shader the same snapshot, not a newer independently interpolated frame. If native evaluation falls behind, hold or drop pending frames; never queue every missed frame. Native geometry must not trail a 60 Hz shader that continues receiving newer body centers.
4. Native evaluation is asynchronous. Observe an owned helper list/frame ID, then promote that snapshot to the GPU. This can align the **data**, but the public API does not provide a proven atomic native-paint/GPU-paint fence. A temporary one-frame mismatch remains possible. Do not promise pixel-exact cross-canvas simultaneity until the integration measures it. If strict same-paint alignment is essential, either hook a verified native render lifecycle or render the moving solids in the same GPU pass; that is a different architecture.

The benefit over (a) is fewer clock owners and fewer asynchronous boundaries. A Desmos ticker followed by a helper observation, JS positions, scalar writes and another native reevaluation still has the expensive geometry write and adds another opportunity for latency. It is reasonable only if a student explicitly wants the existing ticker to control this scene.

In the current code this requires changing the `clockParameterValues`/`setParameterValues` path: once the bridge is enabled, it must use the committed snapshot instead of calling `at(clockSeconds)` again and overwriting it with newer values. Include snapshot time with its frame ID; field terms that still reference shader t must use that same presentation time. Logical clock time may continue accumulating while presentation drops intermediate frames.

**Measured CPU costs, not Desmos costs:** on local Node v24.19.0, building the branch's figure-eight table took about **81 ms**. Over 100,000 warm calls, `figureEight` averaged **0.185 μs** and `keplerPair` **0.417 μs**. These are machine-specific microbenchmarks, not frame-time guarantees; the table should be prepared before animation. `orbit-measurements.json` records the procedure's results. The 60 fps figures in the commit remain your measurements, not new measurements by me.

For three bodies, nine independent coordinate writes imply 270 or 540 scalar updates/second at 30 or 60 Hz; positions plus velocities double those counts. One packed-list expression reduces API calls to 30 or 60 per second, but does not eliminate native surface reevaluation. I have **not measured** that reevaluation cost. Measure p50/p95/p99 write-to-observed-frame latency, native draw latency, dropped frames and end-to-end mismatch with the actual sphere expressions. The entire frame budget is 33.3/16.7 ms, shared with all other work.

For history, the API documents `withHistoryReplacement(callback)`; use it around transient list updates and verify its behavior on the website's calculator object. It replaces the current history entry instead of appending one per update. It is not a blanket guarantee of perfect undo semantics during concurrent student edits. Do not use `clearHistory`, or `setState(...,{allowUndo:false})`, as a suppression workaround. The API also documents that expression analysis completes asynchronously. [Desmos API: history, expression updates and observations](https://www.desmos.com/api/v1.12/docs/index.html?lang=en).

Provider outputs must not be draggable sliders: keep their folder collapsed and publish a list, with scalar aliases defined by indexing. Teacher inputs remain separate. If the student edits an owned output, pause the bridge and flag the ownership conflict rather than overwriting their edit 30 times a second. A teacher dragging a mass or orbital input requests a new provider/schedule at a controlled boundary; don't write that input from the animation loop. During undo/redo or preset replacement, suspend writes, reconcile ownership, then resume.

### Option (b): exact expression files supplied

`figure-eight-desmos-expressions.json` contains **all four 4,096-entry lists**, not placeholders, and every interpolation expression for three bodies. It was exported from the requested source's actual `eightOrbit()` table. `figure-eight-table.json` preserves its interleaved source representation. One-based Desmos indexing, wrap at the last sample, negative time, and the 0.5-radian 3D tilt are accounted for. These lists live only in native Desmos; do not inline them in GLSL.

For each body's phase p=wT/(2π)+(i−1)/3, the definitions compute f=4096(p−floor p), wrap k=floor f to the list range, α=f−floor f, and interpolate `(1−α)X[k]+αX[next]`. The period in the integrated units is 6.32591398, but the displayed period is **2π/w**, or about **10.47198 plugin-clock seconds** at w=0.6. Velocity values in the lists are multiplied by `size*w*6.32591398/(2π)`; do not mistakenly divide by the base period.

`kepler-desmos-expressions.json` provides a reduced mean anomaly and eight fully expanded Newton iterations, with braced subscripts. The supported teaching range is **0≤e≤0.6**, not an unrestricted solver. Use the same reduced phase, starting value E₀=M, and eight iterations in JS if choosing this architecture. The file includes positions, analytic velocity components and the 0.35-radian 3D tilt. At M=0 the separation points along +x and the relative velocity along +y for n>0; the first, heavier body has the negative share −r/(1+r).

How close? With identical full-precision lists and formulas, there is no accumulating integration drift between JS and Desmos: both evaluate the same instantaneous interpolation. Floating-point evaluation order and asynchronous time observations can differ. **I did not measure Desmos-vs-JS numerical error.** On a JS grid of 8,004 cases (e=0,0.3,0.35,0.6; t=0…1000), eight-step/reduced-phase positions differed from the current solver by at most **9.34×10⁻¹³ length units** at a=7.5; the maximum equation residual was **8.89×10⁻¹⁶**. That is a sampled comparison, not a proof for every input. For a residual ε, the mathematical Kepler root error is at most |ε|/(1−e); position error is at most a times that root error. Add floating-point and clock-lag effects separately. Phase reduction is necessary for long-running playback.

Time skew Δt can cause position skew of roughly vmax·Δt, even when both solvers are accurate. Therefore “same formula” alone does not meet your exact-alignment requirement. In a native-owned mode, observe the complete native position list and give **those values** to the uniforms; don't independently sample the plugin clock. That also avoids any JS/Desmos solver discrepancy.

### Moving/Still and existing tickers

For the recommended CPU mode, Moving/Still starts/stops the existing plugin clock and its publication bridge. Still retains the last coherent native/GPU snapshot. Reset must publish `at(0)` to both, even while paused; merely setting the shader's time uniform to zero does not reset position uniforms. A student's existing ticker is left alone.

For the optional native-math/ticker mode, the pill controls the owned ticker or its owned gating scalar, and plugin `t` becomes a mirror of observed native T. Never advance both. If a student ticker already exists, default to CPU mode. Explicit opt-in can append a gated action while preserving their actions; Still then sets only the plugin's gate to zero, not the whole ticker to paused. Ownership is established by an exact saved action/manifest and validation, not merely “the handler mentions my symbol.”

The cylinder fixture is simpler: its field is steady for constant U,R,w, while a geometric marker rotates. Its scratch state supplies a paused native ticker on T. A production CPU-clock installation should omit that ticker and bridge its owned T, or choose native mode consistently.

## C2. Readable, collision-safe names

**Yes: textbook names when free, suffixes only on collision are safe under B4's allocation and ownership rules.** The earlier long names were a conservative example, not a requirement. “Free” must include all existing definitions **and references**, table columns, slider bounds and actions, plus names reserved by other installed presets/providers. A free reference to q₁ is not permission to define q₁ and silently change the student's graph.

Allocate each teacher-facing parameter independently: `q_{1}` first; if unavailable, `q_{E1}`; then `q_{E1a}`, `q_{E1b}`… until absent. Reserve the full map atomically. Keep internal helper names namespaced from the start, so f does not become an accidental public dependency. Reuse the saved map on reload; do not rename it because a shorter name later becomes free. If a student later deliberately adopts an owned name, pause/offer repair instead of silently rebinding either side.

The new scratch fixtures use textbook input names (`I_{1}`, `M_{1}`, R, w, s, etc.) and namespaced helpers. `fixture-manifest.json` records the mapping from B4 names. These files each assume an empty graph; loading several together requires the allocator. Clock-provider names need the same checks: the new code currently merges provider values over graph values under the same canonical keys.

A native Desmos slider displays its actual expression identifier. I found no supported per-slider display-name alias. A point's `label` does **not** rename a slider. The previous live check verified point math labels, not slider aliases. Text-note rows can give readable nearby explanations (included in these states), but I did not freshly verify their rendering, nor a LaTeX-in-note feature. Use plain notes such as “Current in left wire (positive out of the screen)” or a plugin-owned control caption. Do not build a long internal name plus a supposedly hidden native alias and assume the projected slider becomes short.

## C4. Random three-body on `at(t)`

`schedule-contract.json` specifies the provider/renderer boundary. Build a shuffled, immutable sequence of accepted runs **before playback**. Store each run's start, contact time, collision pair and replay samples. Binary-search the segment containing t and return its sample values. Do not integrate, draw, randomize or change a run from inside `at(t)`. Repeatable scrubbing and dropped-frame recovery then work naturally.

Use the existing plugin clock's simulated seconds. With fixed playback speed s, an orbit segment has clock duration t_contact, followed by a flash segment of clock duration **0.7s** (0.7 multiplied by s), so the flash lasts 0.7 active wall seconds. Its age is `(t−flashStart)/s`. Next run starts after that interval. Require `t_contact/s≥35` for the desired margin over 30 seconds. Lock speed for the scheduled bank, or rebuild/revalidate at a run boundary; an arbitrary mid-run speed increase invalidates the original duration guarantee. A simple first release can fix this mode at speed 1.

At collision, use the refined contact positions to compute the colliding pair's mass-weighted center; hide those bodies, freeze/dim the third, fade the old field/trails, and draw the pale ring/sphere with radius `Ri+Rj+0.8*age` and opacity `0.45*(1−age/0.7)^2`. This is a stylized restart effect, not a post-collision dynamical solution. Still freezes the same t, including the flash. The existing clock's 0.1-second elapsed-time cap slows playback after stalls rather than jumping forward; describe duration as active playback and pause on backgrounding if that distinction matters.

The fixed scalar array should also expose body masses/radii, body visibility, run ID, phase, flash center/radius/opacity, trail opacity and frame ID. `schedule-contract.json` lists the semantic order. Map those semantic names to legal allocated Desmos symbols. A run/phase change is handled **outside** `at(t)` by the controller, which clears obsolete GPU trails and updates native list ownership.

Native orbit trails need data beyond scalar uniforms: immutable sample times and body positions, the interpolation rule, and a local-time/index value. Install those native lists once per run/bank, then draw a time window/prefix with an interpolated final endpoint. Do not publish hundreds of trail coordinates every frame and do not join different runs' endpoints. These are actual orbit trails; the decorative field particles are a different object. Resampling the adaptive integrator onto a uniform display table is fine if both renderers share it and interpolation error near encounters is checked. A precomputed schedule can clamp negative t to its initial frame and repeat its whole finite cycle; “new randomized system” means a preselected shuffled sequence, not fresh randomness every query.

### Exact reproduction of the original six screens

`three-body-bank.json` contains **initial states only plus screening metadata**; no trajectories. Use the decimal positions/velocities/masses/radii as stored. Do not attempt to recreate Python's random-number generator from the recorded seed. `reproduce-bank.mjs` is a dependency-free ES module usable in a browser; `screen(case,hmax)` reproduces the prior algorithm.

- Newtonian exterior acceleration, G=1, no softening. Three finite radii are collision thresholds.
- Velocity Verlet: predict `p'=p+vh+ah²/2`; after a collision-free step compute a' and `v'=v+(a+a')h/2`.
- At every step, choose the minimum of hmax, remaining time to 100, and for every pair `0.025*sqrt(r³/(mi+mj))` and `0.025*r/max(relativeSpeed,10⁻¹²)`. This adaptive method is **not a fixed-step symplectic guarantee**.
- Sweep the relative straight segment from d=pᵢ−pⱼ to d'=p'ᵢ−p'ⱼ. With Δ=d'−d, set u=clamp(−d·Δ/max(Δ·Δ,10⁻³⁰),0,1). Contact is detected when |d+uΔ|≤Ri+Rj.
- The reference loops `i=0…2`, `j=0…i−1`; if several pairs pass, the **last** passing pair wins. It returns **t+h**, before accepting the step, not the first-contact root. This is part of reproducing the old result, not recommended event ordering.
- Otherwise accept the step, increment the step counter, measure relative energy error every 100 accepted steps, and stop if any barycentric body radius exceeds 15. Stop at 100 if no collision/escape. The stored energy maximum is sampled, not a bound over all times, and excludes the collision step.

The JavaScript reproduction passed for all six at both step sizes; the largest observed difference from the stored fine-step reference was about **1.17×10⁻¹¹ seconds** in local Node/V8. Each coarse+fine pair took approximately 65–160 ms on this machine. Run load-time verification in a worker, not in the frame loop. Browser execution itself was not measured.

**Reproducibility is not physical event accuracy.** The 3D 20261030 coarse/fine times differ by about 0.0215 seconds, so the earlier results do not establish a 0.01-second numerical-accuracy guarantee for the actual collision. They do establish reproduction of the stored screening algorithm. To improve production contact timing, solve `|d+uΔ|²=(Ri+Rj)²` for the earliest root in [0,1], select the earliest pair, and refine with smaller integration steps around that bracket. A straight-segment root alone still approximates the curved relative path. Re-screen and version the reference results after changing the event algorithm; don't require the improved solver to reproduce the old end-of-step timestamps.

At load, validate array sizes/finiteness/positive masses/radii/no initial overlaps; run both reference step sizes, confirm pair/time within 0.01 of the corresponding stored reference, no premature escape, and the original energy threshold. Check **both** coarse and fine sampled energy errors against 0.002 in the new loader (the original acceptance code only imposed that threshold on the coarse run). Then integrate/store a replay, refine contact if using the production algorithm, and apply the speed-adjusted survival test. Reject failed cases instead of weakening the survival requirement. Keep dimensions separate and use zero z for the 2D cases. A bank version includes the integrator/event rules so later solvers don't silently reinterpret old metadata.

## C5. Specific corrections and agreements

1. **CPU uniforms are the right correction.** The new provider is the missing dynamics/replay boundary from §17. Keep it. “Exact positions” in the comment is too strong for the figure-eight: it is a numerical RK4 table followed by linear interpolation. Also, interpolating stored velocities is not the exact derivative of linearly interpolated positions. A 1,000-phase check at size 6 measured maximum center-of-mass displacement **1.19×10⁻⁶** and velocity-vs-position-derivative discrepancy **0.00620**. If exact derivative consistency matters for carried material, use one Hermite interpolant and its derivative in both consumers, or return the segment slope for piecewise-linear positions; either changes the reference trajectory representation.
2. **The closure test is weaker than its description.** Calling the wrapped provider at one displayed period necessarily returns its initial phase. That does not test the unwrapped RK4 endpoint against its initial state. Retain a raw integration-endpoint test separately before saying “closes to 10⁻⁸.” The base period and speed scaling in `figureEight` are internally consistent.
3. **Kepler signs and mass shares are correct at defaults.** The high-e path is not robust: it starts E=π for e≥0.8 without reducing M. Reproduced e=0.99,t=100,n=0.4 leaves a phase-equation residual of about **−0.3803 radians** after the 30-step cap; other long times also fail. Reduce M, use a safeguarded root solve for general eccentricity, and check convergence. The provided eight-step native option deliberately restricts e≤0.6. The current gallery e=0.3/0.35 cases are not implicated by that high-e failure.
4. **Reset needs a provider publication path.** In the inspected `resetClock`, t and renderer time uniforms reset, but the explicit provider `setParameterValues` call appears in `advanceClock`, not `resetClock`. A paused reset can therefore leave old body-position uniforms unless another refresh happens. Explicitly publish `at(0)` on reset, native geometry included. Also keep provider ownership independent of fragile preset-name/edit heuristics when adding native objects.
5. **The point-dipole change agrees with the requested look.** No finite core and no magnitude absorption is appropriate for that ideal point model. Its origin remains singular; an evaluator clamp is a numerical rule, not a physical interior. The new `exp(−0.1r²)` seed is radially weighted, not uniform and not proportional to |B|. Normalized flow/brightness remains a direction illustration. The 2D axis is y and the 3D axis z; label the axis change. The unchanged AC time dependence is a quasi-static sequence, not an induction/radiation calculation; a static default remains preferable for the teaching preset.
6. **The connected seeds are improvements, with two documentation corrections.** ALONG has soft tails beyond ±2.5; it does not mathematically confine particles there. Removing cos(z) from the vortex lattice makes its velocity an extruded two-dimensional flow, not the previous alternating-layer 3D Taylor–Green field. The blurb and old “three thin layers” comment are now stale and should change. This does not invalidate the desired one-piece appearance.
7. **Keep motion and gravity claims separate.** `carriedWorlds` combines translation, swirl, attraction and a softened exterior fall term with denominator `(r²+0.3)^1.1`. That is a designed velocity field, not Newtonian acceleration, and its far-field fall term scales approximately as r⁻¹·², not r⁻². The newly accurate body paths do not make those carried-particle paths physical gravitational trajectories. A separately labeled gravity overlay should use the §17 exterior acceleration formulas. If asserting an actual scaled orbital model, enforce n²a³=G(M₁+M₂); arbitrary size/speed and field-strength choices do not automatically satisfy it.
8. **Cylinder sign difference is resolved in these files.** The current branch is CCW-positive, whereas the previous report was clockwise-positive. Here the marker, field, circulation Γ=+2πR²w and downward lift for positive w agree with the branch. Surface stagnation has sinθ=+wR/(2U). If you retain the old convention instead, reverse both the circulation terms and marker; don't mix them.
9. **Avoid the figure-eight blurb's uniqueness claim.** “The one stable way found for three bodies to share a single path” is stronger than the code or its tests establish. “A well-known figure-eight choreography of three equal masses” communicates the intended example without that unsupported claim.
